## Problem Statement

The semester planner is meant to be one of the app's biggest features. The first version
(branch `NeonSeigne/plan-semester-separate-branch`, commits 6883516, 0f1377d, 23fd5eb, a317d91)
was never merged and forked before the school packs existed. It cannot be patched into shape:

- UW only: calls `_uw_source` directly; 7 curated programs live in `backend/data/majors/`, not in a school pack.
- Plans live in an in-memory dict: lost on restart, not tied to a user (anyone with a `plan_id` can read or edit).
- One 1,500-line `semester_planner.py` does transcript parsing, requirement matching, difficulty scoring, pack building, LLM refinement and chat patching.
- Requirement rules are only `all_of` / `n_of` course lists; gen-eds are guessed from keywords; every course counts as 3 credits.
- Prerequisite check passes if any one prerequisite is done (AND and OR treated the same).
- No term-offering check, no section clash check, one semester only.
- Two edit paths: a planner chat that regex-parses a ```` ```plan_patch``` ```` block from model free text, plus an `update_semester_plan` tool in the main chat.
- Frontend: a 487-line wizard with ~18 `useState`s, raw `fetch` calls, a 1,108-line CSS file that predates the Campus Companion design, no frontend tests.

Audience: the Neon Gecko sponsor demo, same as the Campus Companion work. The pitch stays "any school, one config".

## What Makes This Cool

**Plan by talking.** The student says "Drop ECON 3010, it's too much with orgo" and the plan
pinned beside the chat changes, with a card that says exactly what that did: requirement
progress, credits, load (and, from M2, graduation term). Every 2026 AI advisor found (Princeton's Tiggy, Harvard's
ChatGPT Edu bot, UCLA's BruinBot) is a chatbot that answers questions; every school's degree
audit (DARS, DegreeWorks, Stellic) is correct but you cannot talk to it. This joins the two: the
model proposes, a deterministic checker decides, and the student accepts.

The test for the demo: **ask → see the change → understand the consequences → accept or undo**,
without a wizard.

## Constraints

- Sponsor demo, local Docker. Must keep UW-Madison, UVA and CU Boulder working.
- Data per school (verified 2026-10-27):
  - **UW (Course Map):** grades, Spring 2027 sections with seats and term dates, **no meeting days, times or rooms**. Prerequisites are a full AND/OR tree (`requirements.nodes`, with `minimum_grade` and `timing: prior|concurrent`), which `_prerequisites_coursemap` currently flattens to a course list.
  - **UVA (theCourseForum CSV):** grades; `2027_spring.csv` exists with 9,220 sections, ~98% with days and times; rooms hidden (`***`) on all but 164. No prerequisites (`csv_snapshot` capability `prerequisites: False`).
  - **CU (FOSE):** sections, no grades, no prerequisites.
- UW meeting times exist only in an internal registrar dataset that needs authorization; no public API found.
- No public source for degree requirements; they must be written by hand.
- API keys (OpenAI/Gemini/Mistral) are for the demo app's own model calls only, not dev tooling.

## Premises (agreed)

1. **The plan is data.** One plan per student per school, stored in Mongo. The chat edits it only through a single typed edit tool; the plan panel and `/plan` page use the same API. No free-text patch parsing, no second edit path.
2. **The checker is the source of truth.** Code, not the model, decides requirements met, prerequisites, credit load, clashes and workload. Each check is **satisfied / violated / unknown**, with its evidence (which rule, which data, data date). Every edit returns a consequence diff the chat narrates and the UI shows.
3. **One profile, three doors.** Chat, transcript upload and a checklist fill the same profile. A transcript parse always ends on the checklist ("I read 14 courses, check these") before planning.
4. **Requirements are hand-checked files in each school pack** (`schools/<slug>/programs/`): 3–5 majors each at UW and UVA, checked against the official guide. Rules: all-of, n-of, credits-from-list, subject+level patterns ("any ECON 4000+"), and a total-credit rule (degree total, which free-elective credits count toward), with explicit double-count and minimum-grade fields. A course matching no named rule is labelled "General elective credit" when the file has a total-credit rule, otherwise "Fills no listed requirement". Labelled "Curated requirements, not an official audit". A school with no program files still plans, with audit checks shown as unknown.
5. **"Everything" scales back per school and says so.** Roadmap and next term everywhere. Week grid and clash check only where section times exist (UVA yes, UW no: the panel says "UW doesn't publish class times"). A missing timetable never reads as "no clashes". Walk times between classes are cut until a source with rooms exists.
6. **Fresh rebuild on `undergrad-experimental`, not a merge.** The old UW program files are a starting point to re-check, nothing more. Workload is a labelled difficulty proxy from grade distributions (UW, UVA), "no grade data" at CU; it is not hours of work.

## Approaches Considered

### Approach A: Edit loop only
Plan store + one typed edit tool + 3-state checker + plan panel beside the chat; next term only; one program per school. Effort M. Ruled out as the whole plan: it drops the roadmap, transcript and what-if the user asked for. Kept as milestone 1 of B.

### Approach B: Planner engine + three surfaces, in milestones (CHOSEN)
A `backend/app/planner/` package behind one API, surfaced in chat (tool + cards), a pinned plan
canvas beside the chat, and a `/plan` page. Effort XL (human ~4–6 weeks / CC ~2–3 days across lanes).

### Approach C: The plan lives only in the chat
Plan as a pinned canvas, no standalone page. Its canvas is adopted as B's M1 surface; "only" was
rejected because a plan also needs a full-page board for when you are not chatting.

### Interaction patterns researched
Instant edits + undo (ChatGPT Canvas / ibl.ai versioning), proposals with Accept/Discard (Tana,
Tiptap, Cursor), term board + command bar (Stellic, Akiflow), compare futures (Outside review; Google
Flights), week-grid first (Motion/Reclaim). Week-grid first rejected: it fails at UW.

## Recommended Approach

**B, with a mixed interaction model:**

- **Layout:** the plan is pinned beside the chat (split view). On phones it is a bottom sheet the chat can open.
- **Model-initiated edits are proposals.** The chat calls the edit tool in `propose` mode; the plan panel shows adds ghosted and drops struck through, and the chat shows a "Proposed change" card with the checker's consequence diff and **Accept / Discard** (M2 adds **Show 2 other ways**; the M1 wireframe shows that button early). Nothing changes until the student accepts.
- **Student-initiated edits apply at once** (clicking remove, picking a section) with **Undo**.
- **Big asks return 2–3 futures to compare** ("lighten my spring", "what if I switch to Data Science"): Lightest term / Keep most options open / Graduate on time, each a full checked plan.
- **`/plan` page (M2):** a Stellic-style term board you can drag, with the remaining-requirements list beside it. Same API, same checker.

### Recommendations from interests

The student can describe what they want ("I like climate stuff and coding, nothing with
essays, mornings are bad") and get courses suggested for the plan's open slots.

- **Interests and preferences live in the profile** (free text plus a few tags the chat extracts: topics, avoid, time of day, load), editable like anything else.
- **Candidates come from real catalog search**, not the model's memory: the model turns interests into searches over course titles and descriptions (`search_catalog`, which already does keyword search at UW and UVA; CU needs a subject code, so the model picks subjects).
- **The checker filters and labels every candidate:** prerequisites (satisfied / violated / unknown), offered next term, time-of-day fit where times exist, workload, and what it fills:
  - "Fills: <rule title>" when a rule in the student's program files matches it;
  - "General elective credit" when the program file has a total-credit rule and the course matches no named rule (never "doesn't count");
  - "Gen-ed: unknown" in M1 and M2, because no gen-ed data exists yet (Open Question 5); with no program file at all, "Requirements: unknown".
- **The model ranks and explains** ("ENVS 2800 fits your climate interest, counts as general elective credit, no Monday mornings; gen-ed status unknown"). Its explanations may only repeat the checker's labels: it never claims a requirement or gen-ed fit the checker did not report, and a test feeds it a course labelled "Gen-ed: unknown" and fails if the reply claims a gen-ed. A chosen pick arrives as a **proposal** like any other edit: Accept adds it to the slot.
- **Places it shows up:** asking in chat and an empty slot in the plan panel ("Suggest courses for this slot") in M1; the M2 "Show 2 other ways" futures also use the stated interests to break ties.

### Engine (backend/app/planner/)

| Module | Owns |
|---|---|
| `programs.py` | Load and validate `schools/<slug>/programs/*.yaml`; catalog year; rule types |
| `requirements.py` | Match completed + planned courses to rules; double-count policy; returns per-rule satisfied/violated/unknown with evidence |
| `prereqs.py` | Evaluate AND/OR prerequisite trees from the provider (UW tree kept, not flattened); unknown where a school has none |
| `offerings.py` | Which terms a course runs, from section data; unknown beyond published terms (roadmap terms are labelled "assumed") |
| `schedule.py` | Section choice and clash check where meeting times exist |
| `workload.py` | Difficulty proxy from grade distributions; credit totals |
| `roadmap.py` | Greedy term-by-term fill to graduation through the checker; produces the "futures" for big asks |
| `edits.py` | The one edit operation set: add, remove, move, swap, pick_section, set_profile; `propose` vs `apply`; revision number + idempotency key; undo stack |
| `diff.py` | Before/after consequence diff for any edit |
| `suggest.py` | Interest-based candidates: catalog searches from the profile's interests, checker labels, ranked shortlist for a slot |
| `store.py` | Mongo persistence: one plan per user per school, revisions for undo |
| `profile.py` | Completed courses from chat, checklist or transcript parse (transcript always ends in a confirm step) |

Providers (`sources/academics.py`) gain a `prerequisite_tree` call and a `sections_for_term` call with meeting times where available; UW's adapter keeps the tree it already receives.

## Behavior details

**Access.** Plan endpoints (`/api/planner/...`) take no plan id from the client: the plan is
looked up from the authenticated user (the app's existing JWT sign-in, including Developer mode
in the demo) plus the deployment's school. A test proves user B cannot read or edit user A's plan.

**Profile.** School (from the deployment), program ids (major and any certificates or minors),
catalog year (defaults to the fall of the student's entry year from their class year, editable),
completed courses with optional grade and term, and interests/preferences. Set in chat ("I'm a
sophomore in Econ") or the checklist (pick program, tick courses). If the major has no program
file, planning still works and requirement checks read "unknown". Rules or prerequisites with a
minimum grade evaluate to unknown when the grade is missing.

**Edits.** `add`, `remove`, `move`, `swap`, `pick_section`, `set_profile`. Every course and
section id is validated against the school's provider before anything else; an unknown id
returns a typed `unknown_course` / `unknown_section` error, never a proposal (tested with a
model-invented code). Each call carries `expected_revision` and an idempotency key.

**Proposals.** Stored with the plan in Mongo (survive reload), each with the `base_revision` it
was checked against. At most one pending proposal per plan: a new one replaces the old (shown as
"replaced"). Discard deletes it; it expires after 24 hours. Slot shortlists and (M2) futures are not proposals: they are a comparison shown in the card, and choosing one option creates the single pending proposal (replacing any earlier one). If the plan's revision has moved when
the student presses Accept, the checker re-runs the proposal against the current plan: if it still
applies, the card refreshes its diff and asks again; if not (e.g. the course was already removed),
Accept is refused with the reason.

**Undo.** The plan keeps a persisted stack of its last 20 non-undo edits and an undo pointer.
Undo writes a new revision that inverts the edit at the pointer and moves the pointer back one, so
repeated Undo walks back through up to 20 edits (undo revisions are never themselves undone).
Any new edit clears the steps after the pointer. No redo. Works from any surface (chat, panel,
/plan page), guarded by `expected_revision`, and survives reload. If an inverse no longer applies
cleanly, undo is refused with the reason.

**Conflicts.** The panel and page refetch the plan and show "Your plan changed in another window"
with the latest version; the student retries. The chat tool gets a `revision_conflict` error,
re-reads the plan, re-proposes once, and says "your plan changed on the plan page; here's the
updated suggestion".

**Consequence diff (M1 fields).** Courses added/removed/moved; each requirement rule whose status
changes (before → after, satisfied/violated/unknown); term credits before → after against the
school's limits; term load label before → after; clash status (or "class times not published");
prerequisite status changes for courses in the term. Graduation term joins in M2 with the roadmap.

**Credits and load.** Per-course credits come from the provider (UVA `Units`, UW Course Map
credits, CU FOSE), shown as a range or "unknown" when absent; never a flat default. Term limits
(full-time minimum, maximum without overload) live in `school.yaml` under `planner:` with a
source URL, and the credit check is satisfied/violated/unknown against them. With credit ranges, the term total is a range: satisfied only if the whole range is within the limits, violated only if the whole range is outside them, otherwise unknown; any course with unknown credits makes the total unknown. **Workload is
informational, not a check:** Light / Balanced / Heavy from how many courses sit in the school's
hardest third by average GPA (0–1 / 2 / 3+), "no grade data" when grades are missing.

**CU Boulder in M1/M2.** The planner is available (Premise 4): profile, edits, credits from FOSE,
suggestions by subject; requirement and prerequisite checks read unknown because CU has no program
files or prerequisite data. M3 adds CU program files, not CU planning itself.

## Success Criteria

- On the demo: "Drop ECON 3010, it's too much with orgo" produces a proposal with a correct consequence diff in under 5 seconds, Accept applies it, Undo reverts it, and a reload shows the same plan.
- The same script works at UW with "class times not published" instead of a week grid, and no false "0 clashes".
- "I like climate stuff and coding" returns at least 3 real courses offered next term, each labelled with one of "Fills: <rule>", "General elective credit", "Fills no listed requirement", "Gen-ed: unknown" or "Requirements: unknown", plus its prerequisite status; no suggested course is invented or out of catalog.
- No check ever reads "satisfied" when the data is missing: unknown is shown as unknown.
- Every program file has a source URL and a "checked on" date; checker unit tests cover each rule type and the prerequisite tree evaluation.
- Two edits racing (chat and page) never silently overwrite each other (revision guard returns a conflict).

### Pass 1: Information architecture (4/10 → 9/10)
- **1A Preview state.** The panel always shows the saved plan. While a proposal is pending, every changed value shows inline as before → after in `--domain-academics-ink` ("20 → 17 credits", "1 → 2 of 4", grid blocks ghosted); the panel header shows "Preview · not applied". The struck row reads "Proposed removal" and the dashed row "Proposed addition" (text, not only styling).
- **2A Card heading.** Small "Proposed change" status label, then a heading naming the action ("Move ECON 3010 to fall, add ECON 3300"), then the single biggest consequence, then the other diff rows; unknown/unchecked lines sit directly above Accept/Discard.
- **3A Navigation.** M1 adds no nav item: a "Plan" toggle in the chat header opens/closes the panel (phone: opens the sheet). M2 adds "Plan" to the desktop rail for `/plan`; the phone tab bar stays at 5 tabs and reaches `/plan` from the Plan toggle and from Saved.
- **4A One term in M1.** The panel heading is the next term ("Spring 2027"); courses moved later appear in a small "Later" list ("ECON 3010 · moved to Fall 2027"). The term strip arrives in M2 with future terms labelled "Assumed".
- **5A Right-panel slot.** The plan occupies the existing right-panel slot (`AnswerPanel`, ChatPage.js:1143) while open; opening a course from the plan or a card shows its details there with "Back to plan", keeping any pending proposal; closing the plan restores AnswerPanel behaviour.

Panel hierarchy (top to bottom): header (term, program, "Preview · not applied" when pending, Undo) → courses this term (+ empty slot rows) → summary line (credits, difficulty estimate, clashes) → Requirements → Weekly schedule → Later.
