## Problem Statement

The app started as a PhD advisory panel and is becoming an undergrad tool. The goal is a
**campus companion**, not just academic advising: academics, student life (union calendar,
events), campus navigation, dining, transit and health services. Every school's deployment
should feel fully unique to that school, and standing up a new school should be configuration,
not new code.

Today that is only partly true. Branding, personas and RateMyProfessor (`school_id`) are
config-only. Everything else is school-specific code:

- Course data: CU uses `backend/app/tools/search_courses.py` with a hard-coded FOSE URL
  (line 23); UW uses five `uw_*` tools over UW Course Map.
- `backend/app/core/improved_orchestrator.py:83-93` hard-codes "UW-Madison" and the `uw_*`
  tool names into the system prompt, so a CU deployment's LLM is told about tools it lacks
  (a live bug).
- `backend/app/api/visuals.py:141-145` keys inline course cards on `uw_*` tool names.
- `backend/app/api/routes/courses.py` and `frontend/src/pages/CourseDetailPage.js:264` are
  UW-only.
- No student life, campus, dining, transit or health data sources exist.

Audience for the first milestone: the team / sponsor (Neon Gecko). The spine of the demo:
**"Any school, one config."**

## What Makes This Cool

Existing AI advisors (Princeton's Tiggy, VMI's Advisely, Duke's Course Advisor) are built for a
single school. They assume each school needs an official registrar/SIS integration, so they
never leave home. This project instead targets **public, student-facing sources** (UW Course
Map, CU's public class search, event iCal feeds, GTFS transit feeds) behind reusable source
types. Most campus data comes in a handful of standard formats, so one connector serves many
schools.

The whoa: in front of the sponsor, a **discovery wizard drafts a new school's pack live**: it
finds that school's event feed, transit feed, dining vendor and RMP id. After a quick review and
a restart, the same app answers "what's happening tonight, where do I eat, and how do I get
there?" with that school's real data and branding.

## Constraints

- Local Docker demo is enough; hosting is out of scope for this milestone.
- Must keep CU Boulder and UW-Madison working throughout (both are existing deployments).
- Live third-party endpoints can be slow, rate-limited or down: the demo needs a recorded
  fallback and a pre-vetted school #3 shortlist.
- Most schools lack public grade-distribution data (UW's is unusual), so every capability must
  be optional and the UI must degrade gracefully.

## Approaches Considered

### Approach A: Generic source tools
About four reusable tools (iCal events, places, GTFS, school pages via RAG) pointed at
per-school URLs. Rejected: no domain concept, and academics and course cards stay
school-specific code.

### Approach B: Domain modules + source-type registry
A `domains:` config section where each domain bundles personas, tools and typed sources,
reusable source types in code, per-domain inline cards, validation and a scaffolder. Not chosen
on its own; it is the foundation of C.

### Approach C: School packs + discovery wizard (chosen)
B's architecture with each school as a folder, plus a wizard that drafts a new school's pack.

## Recommended Approach

**C, built in two layers.** B's architecture is the foundation and must work by itself; the
wizard sits on top.

### Layer 1: Domains and source types (the foundation)

**School pack layout**

```
schools/
  uw-madison/
    school.yaml        # branding, enabled domains, sources, persona overrides
    places.geojson     # buildings, libraries, dining halls, health center
    pages.txt          # URLs for health/services info, ingested into RAG
    logo.svg
  cu-boulder/
    ...
```

`CONFIG_PATH` becomes `SCHOOL=uw-madison` (keep `CONFIG_PATH` working for one release).
Shared defaults (personas, orchestrator settings) live in a base file that `school.yaml`
overrides.

**Domains** (each one turned on and off in `school.yaml`; each owns personas, tools and a card type):

| Domain | Source types | Tools (generic names) | Card |
|---|---|---|---|
| academics | `fose`, `uw_coursemap` (later `banner_ssb`) | search_courses, course_sections, prerequisites, course_grades*, next_courses* | course card (exists) |
| student_life | `ical`, `rss` | events_search, events_tonight | event card |
| campus | `geojson` (imported from OSM) | find_place, walking_directions | map / route card |
| transit | `gtfs` (+ `gtfs_rt` optional) | next_departures, route_between | departure card |
| dining | `nutrislice`, `json_api` | dining_hours, menu_today | menu card |
| health | `web_pages` (existing RAG) | health_services_lookup (RAG + crisis lines in config) | info card |

\* optional capability. A tool registers only if its domain is on **and** its source supports
it.

**Code changes**

- `backend/app/sources/`: one module per source type, each with a small protocol
  (`fetch`, `capabilities`, plus a cache TTL). Move FOSE logic out of `search_courses.py` (base
  URL from config) and wrap `_uw_source.py` as `uw_coursemap`.
- `backend/app/tools/`: replace school-named tools with the generic names above, dispatching
  on the domain's configured source. Keep the existing auto-discovery registry; registration
  filters on domain + capability.
- `backend/app/config.py`: add `DomainConfig` / `SourceConfig` models with validation (fail
  fast on startup with a clear message, like the existing RMP `school_id` check).
- `backend/app/core/improved_orchestrator.py`: build the tool-guidance part of the system prompt
  from the enabled domains and tools, not hard-coded UW text. This fixes the CU bug.
- `backend/app/api/visuals.py`: key card specs on generic tool names and add the new card
  types.
- `backend/app/api/routes/courses.py` + `CourseDetailPage.js`: provider-agnostic; attribution
  (name, URL) comes from the source's config.
- Frontend: event, map/route, departure, menu and info cards. Theme and copy stay config-driven.
- `scripts/import_places.py <slug>`: builds `places.geojson` from OpenStreetMap via the
  Overpass API. It takes named features inside the school's `amenity=university` boundary:
  buildings, libraries, dining (`amenity=restaurant|cafe|fast_food`), health (`amenity=clinic|doctors`),
  bus stops. Output schema per feature: `name`, `aliases[]`, `category`
  (academic|library|dining|health|housing|recreation|transit|other), `lat`, `lon`, optional
  `hours`. Run once for CU and UW, then hand-curate the ~30 places students ask about most
  (add aliases like "UMC", "Mem U"). The wizard runs the same import for new schools.

### Runtime rules (apply to every school)

- **Selecting and enabling a school:** `SCHOOL=<slug>` picks the pack. `school.yaml` has
  `status: draft|active`. The loader refuses a `draft` pack unless `ALLOW_DRAFT=1` (set only in
  the demo's school #3 service). Every source has `verified: true|false`. A domain whose
  required source is `verified: false` is disabled at startup and logged, never half-loaded.
  `scripts/new_school.py --activate <slug>` flips `status` to `active` after review.
- **Timezone:** `school.yaml` requires `timezone` (IANA, e.g. `America/Denver`); startup fails
  without it. "Tonight", "today" and "next departure" are computed in that zone. Floating iCal
  times are read as school-local. All-day events appear under "today" labeled all-day and are
  never placed at midnight.
- **Per-school data isolation:** Chroma collections and the Mongo database name are prefixed
  with the slug (`<slug>_docs`, `<slug>_advisor`), so one school's ingested pages can never
  answer for another. Health/services pages in `pages.txt` are ingested at startup when the
  collection is empty or the file's hash changed.
- **Health safety:** the health domain fails validation and stays disabled unless
  `health.crisis_lines` (name, phone, hours) is present and `verified: true` in `school.yaml`.
  The wizard never fills crisis lines; it leaves a TODO. Any crisis-adjacent query (self-harm,
  emergency, assault) is detected by keyword match OR an LLM classifier flag: either one
  alone triggers it. If the classifier errors or takes longer than 2s, detection falls back to
  keywords only and never suppresses the crisis text. A triggered query is answered with the
  configured crisis text verbatim before any LLM content. If the health domain is off, the configured
  crisis text (or 988 / 911 as a hard-coded US default) is still shown for those queries.
- **Feed failures:** each source has a 5s timeout and an on-disk cache (TTL per type: events
  15 min, GTFS static 24 h, menus 1 h, catalog 24 h). On failure, serve the stale cache with an
  "as of <time>" note on the card. Only with no cache at all does the tool answer "I don't have
  that for this school right now." `scripts/warm_cache.py <slug>` fills the cache before a
  demo. `SOURCES_OFFLINE=1` serves campus data from cache only and skips `pages.txt`
  ingestion (it uses the persisted Chroma collection). It does **not** remove the need for
  the LLM API (Gemini) or the crisis classifier; "offline" here means no third-party campus
  data calls. The cache directory is keyed by slug and bind-mounted, so it survives restarts.

### Layer 2: Discovery wizard

`scripts/new_school.py "<School Name>" --homepage <URL>`. The homepage is required; with no
homepage the wizard exits with a usage message. Milestone 1 discovery is deterministic: no
LLM and no search-API key. Time limits:

- **Overall deadline: 90s wall clock.** Sources are probed concurrently (at most 6 in flight).
- Homepage crawl: depth 2, at most 40 GETs, 5s timeout each. It counts only crawl and probe
  requests.
- External services have their own timeouts and are not in the 40 cap: RMP lookup 10s,
  Nominatim 5s (one request, User-Agent carrying a project contact address from config, never a personal address; respects its 1 req/s policy), Overpass 30s,
  Mobility Database catalog CSV 15s (cached locally after the first download).
- When the deadline hits, every source not yet probed is written `verified: false` with a
  TODO, and the pack is still written.

After probing, the wizard warms the cache for every verified source (counted inside the 90s).
Running it again for an existing slug **merges** instead of overwriting. It rewrites only
machine-probed fields (source URLs and their `verified` flags) and never touches
human-owned fields: `crisis_lines`, branding, persona overrides, `status`, and any source
entry marked `locked: true` by a reviewer. If a re-probe fails for a source that was
`verified: true` and still has a cache, that source stays verified with `stale: true`, and its
cache serves with an "as of" note. The domain does not drop out. The merge is printed as a
diff in `REPORT.md`.

| Source | Discovery method (milestone 1) |
|---|---|
| RMP `school_id` | reuse `scripts/rmp_school_lookup.py` with the school name |
| events (`ical`/`rss`) | probe `events.<domain>`, `calendar.<domain>`, `<homepage>/events`, `<homepage>/calendar/`; on each page look for `<link rel="alternate">` of type `text/calendar` or RSS, `.ics` links, the Localist pattern `/api/2/events`, and Trumba embeds (`webName: "<name>"` → `trumba.com/calendars/<name>.ics`, which is how UVA was found) |
| catalog (`fose`) | probe `classes.<domain>/api/?page=fose&route=search` and `cab.<domain>/api/?page=fose`. Banner detection is out of milestone 1 |
| places (`geojson`) | run `scripts/import_places.py` against the school's OSM university boundary (name match via Nominatim) |
| transit (`gtfs`) | match the school's city (from Nominatim) against the Mobility Database catalog CSV |
| dining (`nutrislice`) | probe `<school-short-name>.nutrislice.com/menu/api/schools` |
| health (`web_pages`) | links within depth 2 whose URL or text contains health, counseling, wellness or medical, written to `pages.txt` |

Output: a `schools/<slug>/` pack with `status: draft`, every source marked `verified: true` only
if its probe returned parseable data, a TODO for crisis lines, and `REPORT.md` listing each
probe and its result. Branding (colors, logo) is suggested from the homepage and never
auto-published. Anything not found becomes a disabled domain with a TODO, never a crash.

### Demo script (about 7 minutes)

Topology: `docker-compose.demo.yml` runs one backend + frontend pair per school, sharing one
Mongo (isolated by database name): CU on ports 3001/8001, UW on 3002/8002, school #3 on
3003/8003 with `ALLOW_DRAFT=1`. Switching schools means switching browser tabs, with no
restart.

- `schools/` is **bind-mounted read-only** into every backend, so a pack the wizard writes is
  visible without an image rebuild. The cache directory is a **read-write** volume, and each
  backend writes only its own `cache/<slug>/` subdirectory, so caches refresh at runtime.
  Chroma's data directory is also a persistent volume.
- Each service's `SCHOOL` slug is fixed in `docker-compose.demo.yml` ahead of time, including
  `school3`'s chosen slug. Each frontend is built with `REACT_APP_API_URL` pointing at its own
  backend port.
- **Rehearsal flow:** run the wizard for school #3's slug the day before, review the pack,
  then run it again on stage with the same slug. The on-stage run merges into the reviewed
  pack, keeping every rehearsal edit, and re-warms the cache. A failed probe falls back to
  the rehearsal cache as `stale: true`. Then
  `docker compose up school3` starts the pair (expected ~20-30s; time it in rehearsal).
- On stage, the human review step is a 30-second look at `REPORT.md`; the full review happens
  in rehearsal.

1. CU Boulder: "What's happening tonight and how do I get there from the UMC?" shows event +
   route cards.
2. Same question on UW-Madison: different events, places and branding.
3. Run the wizard on a pre-vetted school #3, show the draft pack and its verified flags,
   restart, ask the same question.
4. Show the diff for school #3: a folder of YAML and data, zero Python.
5. Fallback: a pre-recorded run of step 3 if any endpoint fails on the day.

### R3-1 — feasibility (blocking)

**Problem**

> The cache directory is mounted read-only into every backend, but the Feed failures rule has each backend keep an on-disk cache with per-type TTLs (events 15 min, menus 1 h) that it refreshes on fetch. With a read-only mount, every cache write fails: caches cannot refresh during the demo, and a cache miss can never be filled at runtime.

**Remedy**

> Mount schools/ read-only and the cache directory read-write (for example each backend writes only its own <slug> subdirectory), or state that backends keep a separate writable runtime cache and treat the mounted one as a read-only seed.

### R3-2 — consistency (blocking)

**Problem**

> The rehearsal flow presents the rehearsal cache as a fallback if an on-stage probe fails. But the on-stage run overwrites the pack, a failed probe writes that source as verified: false, and the loader disables any domain whose required source is verified: false. The leftover cache is never used, so the domain still drops out of the live demo.

**Remedy**

> Define overwrite behavior for a failed re-probe: either keep the prior verified: true (flagged stale) when a cache for that source exists, or say plainly that a failed on-stage probe disables the domain and the demo switches to the recorded fallback.

### R3-3 — consistency (blocking)

**Problem**

> The full human review is supposed to happen in rehearsal, but the on-stage run with the same slug overwrites the draft pack. Every rehearsal edit (crisis lines filled and verified, branding accepted, hand-fixed sources) is lost, and the pack that goes on stage is unreviewed.

**Remedy**

> Specify that re-running preserves human-edited fields (for example crisis_lines, branding, and manually set source entries) and rewrites only machine-probed fields, or have the on-stage run write a fresh draft that is diffed against the reviewed pack.

### R3-4 — completeness (minor)

## Post-review change: UVA academics source

Requested by the user on 2026-10-26 ("do courseforum"), after the eng review. This turns on
academics for UVA in milestone 1 and replaces "academics is disabled for UVA".

**Source: new `csv_snapshot` academics provider** in `backend/app/sources/` (third provider beside
`fose` and `uw_coursemap`, so the sources layer from D3 covers it). It downloads public CSVs from
`github.com/thecourseforum/theCourseForum2` (GPL-3.0 repo), caches them, and refreshes daily:

| File | Fields | Freshness |
|---|---|---|
| `tcf_website/management/commands/semester_data/csv/2026_fall.csv` (4.2 MB) | ClassNumber, Mnemonic, Number, Section, Type, Units, Instructor1-4, Days/Room/MeetingDates 1-4 (rooms masked `***`), Title, Topic, Status, Enrollment, EnrollmentLimit, Waitlist, WaitlistLimit, Description, Disciplines, Cost | last updated 2026-09-03: seat counts are stale, show "as of" |
| `.../grade_data/csv/<term>.csv` (2009 to 2026 Spring) | Term, Subject, Catalog Number, Class Title, Primary Instructor, Section, Course GPA, # of Students, A+ ... C-, DFW | per semester; source is UVA IRA's public grade distribution |

**Old data, labeled as such (user decision 2026-10-26):** these files are a snapshot, not live
data. Every UVA academics answer and card shows "Data as of <file's last commit date> from
theCourseForum" (Fall 2026 sections: 2026-09-03), and enrollment, seats and waitlist are
described as historical, never as current availability. The tool description tells the LLM the
same, so it never says a section "has open seats now". `warm_cache.py` records the commit date
it fetched.

Mapping: `Mnemonic` + `Number` to `{subjects:[Mnemonic], course_number}` so existing course cards,
`courseLabel` and the grade charts work unchanged. Tools available for UVA: search_courses,
course_sections, course_grades. Not available: prerequisites, next_courses (not in the data).

**Difficulty, available now (no permission needed):**
- Per professor: the existing RateMyProfessor tool already returns `avgDifficulty`,
  `wouldTakeAgainPercent`, `avgRating`, `numRatings` (rate_my_professor.py:46-49). UVA needs its
  RMP `school_id` (look up with `scripts/rmp_school_lookup.py`).
- Per course: derived from grade CSVs, labeled as derived: mean GPA, %A range, DFW rate, trend
  across terms, and per-instructor GPA for the same course.

**Not available without written permission from theCourseForum:** their review data, which
lives only in their database and on server-rendered pages: per-review `difficulty`,
`instructor_rating`, `enjoyability`, `recommendability` (1-5), `hours_per_week`,
`amount_reading` / `writing` / `group` / `homework`, review text, and `ReviewLLMSummary`
(tcf_website/models/models.py:1108-1190, 1385). There is no public API (Django REST is
installed but no routes in tcf_core/urls.py). Their Terms of Use prohibit "automated scripts
to collect information" and incorporating Site Content "in any other database" without prior
written permission. **Not pursued for M1** (user decision 2026-10-26: use what is public for now). Later, optionally: ask theCourseForum's team for a data agreement (reviews and
workload) and confirm reuse of the repo CSVs. Until then the app links to the course's
theCourseForum page instead of quoting it.
